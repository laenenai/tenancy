## Executive summary

**Is this production grade today? No.** It is a well-researched early-stage module with an unusually good security design in places, but the fail-closed claims are not yet true in all configurations, the credential boundary is porous, and the external-adoption story is incomplete. The full race/container suite passing is necessary but nowhere near sufficient for a cross-tenant disclosure control.

The five things that matter most:

1. **The RLS safety story has fail-open holes and false-pass checks.** A tenant already in the positive cache is served after it is suspended or marked deleting for up to the cache TTL, despite docs saying suspension is never cached (DOM-01). `CheckEnforcement` can report `FailClosed()==true` with no tables checked, with a policy that only has the right *name*, or when `AppRole` owns a FORCEd table and can still disable RLS (DOM-02, SEC-01). `AssertRLSCoverage` accepts any policy, including a permissive `USING (true)` policy or the `tenant_access` companion alone (DOM-02).
2. **Credential material is exposed through the data-plane and extension seams.** `Scoped.Pool()` returns the full pool row, including `MetadataDSN`; `Credentials.Issue` and `OpenBao.RoleFor` receive that same full row (ARCH-03). The runtime `AppRole` is granted `SELECT/INSERT/UPDATE` on both registry tables, `metadata_dsn` is stored in plaintext, and `pool_id`/`metadata_dsn` have no immutability protection (SEC-02). The maintainer has chosen separate control-plane and data-plane roles/DSNs (Q2), so this is now a P0 implementation item rather than a conditional risk. If the registry is reachable with the data-plane role, SQL injection in a tenant query is a registry-wide compromise.
3. **Shutdown and credential-lease lifecycle can lose work and leave live credentials.** `CachingResolver.Close` can return before a retired pool has actually been closed and its credential released (DOM-04). Failed `Release` calls are deliberately discarded, with no hook or metric (MNT-04). On the pool-open error path, `Release` inherits the request context, so a canceled request can leave the lease live until its TTL (SEC-07).
4. **External adoption is blocked by the first-use path and the public documentation surface.** The README quickstart is not a runnable program (undefined `tenantID`, ignored errors, no tenant creation), and it never explains that `Migrate` creates `AppRole` as `NOLOGIN` and that the runtime login role needs membership/inheritance (DOC-01, DX-01). The alias-only facade means `go doc . Config` and pkg.go.dev show `type Config = scope.Config` with no fields or methods (ARCH-01, DOC-07). Tags `v0.1.0`–`v0.3.0` exist while the README says "No tag yet" (DOC-02).
5. **Supply chain and release engineering are not production-grade.** Four reachable vulnerabilities are reported, one on the production pgx path (`x/text` via SCRAM), and CI has no `govulncheck` step (SEC-08, MNT-01). Tool versions are duplicated between `mise.toml` and CI, generated code is not checked in CI, there is no changelog/release workflow, and one maintainer owns a cross-tenant disclosure control (DX-04, MNT-02, MNT-03).

What is genuinely strong: the control-plane/data-plane type split and its compile-failure test; the redaction convention and its negative-fixture tests; the conformance suite's anti-vacuity controls for RLS; the extraction of TOCTOU and partial-borrow regressions; the decision records and measured spikes; and the `-short`/`test-all` split with `-count=1` and race detection. Those are real assets and should be preserved while the P0 issues are fixed.

### GO — Go best practices and idiomatic Go

**Score: 3/5.** The module is idiomatically conservative and the plane separation is a genuine type-level design, but several API choices make it easier to misconfigure or retry forever.

#### GO-01 — The exported RLS-exemption map is mutable global state
- **Severity:** MAJOR
- **Evidence:** `tenancy.go:305` — `var RegistryTablesExemptFromRLS = pg.RegistryTablesExemptFromRLS`; `internal/pg/rls.go:95-102` declares the map.
- **Why it matters:** Any consumer can add an exemption or delete an existing one, silently weakening `AssertRLSCoverage`, and the map is not safe for concurrent mutation. A security check whose allow-list is writable by the code it checks is not a check.
- **Recommendation:** Keep the map unexported and expose either `RegistryTablesExemptFromRLS() map[string]string` returning a copy, or `RLSExemptionReason(table string) (string, bool)`. Add a test that mutation by a consumer cannot change coverage.
- **Breaking:** Yes — the exported variable changes to a function; pre-1.0 acceptable.
- **Effort:** S

#### GO-02 — Permanent failures are classified as retryable `ErrUnavailable`
- **Severity:** MAJOR
- **Evidence:** `internal/registry/registry.go:353-374` maps SQLSTATE `42501` (insufficient privilege) to `domain.ErrUnavailable`; `internal/pg/rls.go:215,220` maps a missing table/column to `ErrUnavailable`; `internal/pg/scoped.go:182-184` maps a failed `SET LOCAL ROLE` to `ErrUnavailable`; `internal/domain/errors.go:44-53` defines `ErrUnavailable` as "a caller may retry".
- **Why it matters:** A wrong role, missing grant, or schema that lacks `tenant_id` will be retried forever by callers and retry middleware, and alerting will call a permanent deployment mistake an outage.
- **Recommendation:** Split the taxonomy: map privilege/role/schema-shape failures to `ErrInvalidConfig` (or add a distinct `ErrPermission`), keep `ErrUnavailable` only for reachability and suspension, and add `errors.Is` tests for the 42501 and `SET ROLE` paths. Validate names and lengths before reaching Postgres.
- **Breaking:** Yes — callers branching on `ErrUnavailable` will change behavior; this is the right time.
- **Effort:** M

#### GO-03 — `IsRLSViolation` treats every SQLSTATE 42501 as an RLS policy refusal
- **Severity:** MAJOR
- **Evidence:** `internal/pg/enforcement.go:41-59` returns true for any `*pgconn.PgError` with code `42501`; `internal/pg/pg_test.go:175-200` asserts exactly that; `tenancytest/credentials.go:541-550` uses `tenancy.RLSViolationCode` for a `CREATE TABLE` privilege error.
- **Why it matters:** 42501 is also returned for missing table grants, DDL refusal and ownership errors. A test or startup check can pass because a grant was missing rather than because the tenant policy held, and a caller can misdiagnose a privilege problem as an isolation success.
- **Recommendation:** Rename the broad predicate to `IsInsufficientPrivilege`, and add `IsRLSPolicyViolation` that additionally requires the Postgres policy-refusal shape (for example the "row-level security policy" message, or a policy name check). Keep `RLSViolationCode` as the SQLSTATE constant but document the overlap. Add a negative fixture for a missing grant.
- **Breaking:** Yes — the name/semantics of the exported predicate change.
- **Effort:** S

#### GO-04 — `CacheOptions` mixes cache, lifecycle, clock and credential configuration, with inconsistent zero values and a validation bypass
- **Severity:** MAJOR
- **Evidence:** `internal/pool/resolver.go:135-207` — `TTL` zero means no caching, `MaxPools <= 0` means unbounded, `MaxTenants <= 0` means `DefaultMaxTenants`, and `Credentials`/`LongestTransaction` live inside the cache options. `internal/scope/scope.go:158-173` validates only `cfg.Credentials`; `scope.go:194-200` lets `cfg.Cache.Credentials` silently override it.
- **Why it matters:** Three different meanings for zero in one struct invite production misconfiguration. Setting `Cache.Credentials` directly bypasses the required `LongestTransaction` startup check and is only discovered at first resolution. Negative TTL is accepted. The API makes the safe path harder than the unsafe one.
- **Recommendation:** Make `CacheOptions` contain cache knobs only; move `LongestTransaction` and `Credentials` to a `PoolLifecycleConfig`/`Config` field. Validate all durations are non-negative, `MaxConns >= MinConns`, and the effective credential source in one place. Either bound `MaxPools` by default or require an explicit unbounded choice. Reject duplicate/conflicting credential configuration.
- **Breaking:** Yes — configuration shape changes; pre-1.0 acceptable.
- **Effort:** M

#### GO-05 — Public ID constructors can panic, and input types have constructor-shaped names
- **Severity:** MINOR
- **Evidence:** `internal/domain/ids.go:52-65` uses `ulid.MustNew`, which panics if `crypto/rand` fails; `NewTenantID`/`NewPoolID` are public. `tenancy.go:178-187` exports `NewPool` and `NewTenant` as *input structs*, not constructors, while `tenancy.go:148-151` names the mixed cache/lifecycle struct `CacheOptions`.
- **Why it matters:** A library constructor that can panic on an entropy failure violates the "return errors at boundaries" convention and is hard for a server to handle gracefully, even if the failure is catastrophic. The naming is actively confusing: `NewPool` looks like a constructor but is a DTO.
- **Recommendation:** Decide and document the panic policy; preferably use `ulid.New` and return `(ID, error)` (or provide `MustNewTenantID` separately). Rename the inputs to `PoolSpec`/`TenantSpec` (or `CreatePoolInput`/`CreateTenantInput`). Do the rename in the same breaking-change window as the config cleanup.
- **Breaking:** Yes — public constructors and type names change.
- **Effort:** S

### CLN — Code cleanliness

**Score: 3/5.** The code is readable and the comments usually explain *why*. The remaining cleanliness problems are mostly drift and dead surface, not tangled implementation.

#### CLN-01 — `Readiness` is dead public surface and a false charter claim
- **Severity:** MAJOR
- **Evidence:** `internal/domain/readiness.go:1-40` declares `Readiness` and four states; its doc says "It is in this module, and in the charter's scope list", but `CHARTER.md:3-13` lists no readiness concept and forbids consumer domain concepts. It is re-exported at `tenancy.go:240-243,352-355`; the only other references are `internal/domain/domain_test.go:139-152`. No migration, query, or method uses it.
- **Why it matters:** This is direct charter drift and an exported API obligation with no behavior. It invites consumers to depend on a state machine this module does not implement, and sets a precedent for further scope creep.
- **Recommendation:** Remove `Readiness` and its constants. If a consumer needs it, put it in that consumer's module (likely `iam`) or amend `CHARTER.md` explicitly and give it a real registry use.
- **Breaking:** Yes — public type and four constants removed.
- **Effort:** S

#### CLN-02 — Stale comments, dead CI logic and an unexercised historical spike module
- **Severity:** NIT
- **Evidence:** `internal/pg/rls.go:104-107` says "the single policy" while `rls.go:190-206` creates two; `rls.go:178-182` says "Four unwrapped Exec calls" while there are six statements; `internal/pg/enforcement.go:154-157` says both probe transactions are rolled back while `CheckEnforcement` runs the scoped probe through `Scoped.Tx`, which commits (`scoped.go:149-152`). `.github/workflows/ci.yml:26-40` contains a "detect Go packages" branch that is always true in this repository. `docs/superpowers/spikes/2026-10-23-openbao-db-credentials/go.mod` is a nested module not covered by root `go test`/`vet`.
- **Why it matters:** Comments that contradict code train reviewers to distrust the docs; a dead CI branch and an unexercised nested module add maintenance surface without adding signal. The historical spike is still valuable as evidence, but it should not look like shipping code.
- **Recommendation:** Correct the three comments, delete the always-true CI branch, and either move the spike under a non-Go docs tree, add it to a CI job, or mark it clearly as historical. Keep the measurements; remove the ambiguity.
- **Breaking:** No.
- **Effort:** S

#### CLN-03 — `MigrationStatus` requires an `AppRole` it does not use
- **Severity:** MINOR
- **Evidence:** `internal/migrate/migrate.go:161-177` calls `cfg.resolve()`; `migrate.go:215-231` requires `AppRole`; `pgmigrate.Status` does not need the application role, only migration credentials.
- **Why it matters:** An operator with only the migration DSN cannot inspect migration status without inventing an `AppRole` value. That is unnecessary friction in exactly the incident path where status is most useful.
- **Recommendation:** Split `Status`'s input into a `StatusConfig{DSN, Postgres}` (or make `AppRole` optional for `Status`) and add a test that `Status` works without it. Keep `Up` requiring `AppRole` because its reconciler asserts grants.
- **Breaking:** Yes — the `Status` signature/config shape changes; pre-1.0.
- **Effort:** S

### ARCH — Architecture and internal consistency

**Score: 3/5.** The dependency direction and plane separation are real design assets. The public surface and test-harness boundaries are not yet coherent enough for external adoption.

#### ARCH-01 — The alias-only facade makes the public API undiscoverable
- **Severity:** MAJOR
- **Evidence:** `tenancy.go:137-210` aliases `Tenancy = scope.Tenancy`, `Config = scope.Config`, `Scoped = pg.Scoped`, `PoolConfig = pg.PoolConfig`, `CacheOptions = pool.Options`, etc. `go doc . Config` renders only `type Config = scope.Config` with no fields; `go doc . Tenancy` does not show `Scope`, `Control` or `Close`. The doc comments then say "See scope.Config" / "See pg.Scoped", which are internal packages an external consumer cannot import.
- **Why it matters:** External adopters use `go doc` and pkg.go.dev, not the repository. The public types are effectively undocumented: required fields, optionality and method sets are invisible. This is the largest external-adoption defect in the module.
- **Recommendation:** Define the public-facing configuration and handle types in a public package or the root package, and alias them internally if the identity matters. At minimum, add a root `doc.go` with complete field/method listings and runnable examples; the aliases can stay for compatibility. Do not rely on pointers to `internal/` for API documentation.
- **Breaking:** No if alias names and import paths are preserved; moving implementation is invisible. If concrete types are introduced instead, it is breaking but pre-1.0.
- **Effort:** L

#### ARCH-02 — `testdb` puts the Docker/testcontainers graph in the production module and exposes internal types in its public API
- **Severity:** MAJOR
- **Evidence:** `go.mod:10-11` directly requires `github.com/testcontainers/testcontainers-go` and its Postgres module because `testdb/testdb.go:74` imports `tcpostgres`. `testdb/testdb.go:110` declares `type Migrator func(ctx context.Context, dsn domain.DSN) error` and `:155` returns `domain.DSN`; both are recorded in `api.txt`. A consumer importing only `github.com/laenenai/tenancy` still resolves the Docker/moby/testcontainers graph.
- **Why it matters:** Every production consumer inherits a large test-only dependency graph, its CVEs and its supply-chain surface. The public `testdb` API is not self-contained because it names an internal package. The harness is valuable; its placement is wrong.
- **Recommendation:** Make `testdb` a nested module (`testdb/go.mod`) so the import path stays `github.com/laenenai/tenancy/testdb` while Docker dependencies leave the root `go.mod`. Change exported signatures to `tenancy.DSN`. Keep `tenancytest` in the root module; it only needs the root package and `testing`. Add a CI job for the nested module.
- **Breaking:** No source break with a nested module and alias-identical `tenancy.DSN`; consumers must `go get` the nested module version. A separate repository/path would be breaking.
- **Effort:** M

#### ARCH-03 — The data-plane and credential-extension seams expose `MetadataDSN`
- **Severity:** MAJOR
- **Evidence:** `internal/pg/scoped.go:84-85` — `func (s Scoped) Pool() domain.Pool { return s.poolRow }`; `internal/domain/pool.go:46` exposes `MetadataDSN`. `internal/domain/credentials.go:63` defines `Issue(ctx, p Pool)`, and `credentials/openbao/openbao.go:197,355,433` uses the full `Pool` for `RoleFor`/`Issue` even though it only needs `p.ID`.
- **Why it matters:** Any request handler holding a `Scoped` can write `string(scoped.Pool().MetadataDSN)` and open a raw pgx connection that bypasses `Tx`'s role narrowing and tenant GUC. A custom `Credentials` implementation receives the long-lived static password that dynamic credentials are supposed to remove from the process. The type split prevents SQL on `Control`, but does not separate capabilities.
- **Recommendation:** Introduce a `PoolRef` (ID, name, region, blob config reference, capacity) with no DSN. Return that from `Scoped.Pool()` and pass it to `Credentials.Issue`/`RoleFor`; keep the full `Pool` only in the resolver/opener internals. Add a compile-failure or API test that `MetadataDSN` is not reachable from `Scoped`.
- **Breaking:** Yes — public `Scoped.Pool()` and custom `Credentials` implementations change. Pre-1.0 acceptable.
- **Effort:** M

#### ARCH-04 — `Credentials` and `Clock` have two configuration homes with silent precedence
- **Severity:** MAJOR
- **Evidence:** `internal/scope/scope.go:96-122` declares `Config.Credentials` and `Config.Clock`; `internal/pool/resolver.go:168-184` also declares `Options.Credentials` and `Options.Clock`. `internal/scope/scope.go:194-200` does `if cache.Credentials == nil { cache.Credentials = cfg.Credentials }` and the same for `Clock`, so `Cache.Credentials`/`Cache.Clock` silently win. The startup validation at `scope.go:158-173` checks only `cfg.Credentials`.
- **Why it matters:** There are two ways to set the same behavior, one bypasses validation, and the precedence is not documented as a contract. A deployment can run with a credential source it did not intend.
- **Recommendation:** Keep one home for each: `Config.Credentials`, `Config.Clock`, and a separate `PoolLifecycleConfig.LongestTransaction`. Remove the duplicates from the public `CacheOptions` alias. Validate the effective values once in `Open`. If a transition period is needed, error when both are set rather than silently preferring one.
- **Breaking:** Yes — `CacheOptions.Credentials`/`Clock`/`LongestTransaction` move; pre-1.0.
- **Effort:** S–M

#### ARCH-05 — `api.txt` records AST exports, not the reachable public surface
- **Severity:** MAJOR
- **Evidence:** `api_test.go:51-62` lists entire internal packages; `api_test.go:232-245` accepts any exported method of an exported type. As a result `api.txt` includes unreachable internals such as `pg.NewScoped`, `pool.Handle`, `pool.NewResolver` and `registry.Open`. Conversely, reachable facade values are missing: `domain.Redacted` (`internal/domain/dsn.go:13`) and `pg.TenantAccessPolicyName` (`internal/pg/rls.go:30`) are not re-exported, and `tenancytest/suite.go:137-141` duplicates the `"[REDACTED]"` literal because of it. `migrate.Applied = pgmigrate.Applied` (`internal/migrate/migrate.go:124`) can change public surface without appearing in the golden file.
- **Why it matters:** The charter calls `api.txt` a boundary mechanism, but it flags private implementation changes while missing public reachability changes. That produces review noise and false confidence. Consumers also cannot name the permissive policy or the redaction placeholder.
- **Recommendation:** Generate the golden file from `go/types` reachability starting at the root package, following aliases, and list other importable packages separately. Re-export `Redacted` and `TenantAccessPolicyName` (or make them truly internal). Add a negative test that an unreachable internal export does not appear and a reachable one does. Decide whether `Applied` should be an owned type rather than an external alias.
- **Breaking:** No for the tooling and additive exports; changing `Applied` representation would be breaking.
- **Effort:** M

### SEC — Security

**Score: 3/5.** Secret handling is better than most libraries at this stage. The remaining issues are about what the security checks actually prove, and about credential material crossing boundaries it should not.

#### SEC-01 — An `AppRole` that owns a FORCEd table is treated as fail-closed, but the owner can disable RLS
- **Severity:** MAJOR
- **Evidence:** `internal/pg/enforcement.go:311-315` only reports ownership when `!RowSecurityForced`; `internal/pg/pg_test.go:283-295` asserts that owner + FORCE remains `FailClosed`. `FORCE` subjects the owner to policies for DML, but it does not prevent the owner from `ALTER TABLE ... DISABLE ROW LEVEL SECURITY`, `DROP POLICY`, or `ALTER POLICY ... USING (true)`.
- **Why it matters:** If the data-plane `AppRole` owns a tenant table — a common outcome when the same role runs consumer migrations or has DDL — a compromised app role or SQL injection can switch the backstop off and read every tenant, while `CheckEnforcement` still says fail-closed. The check reports the wrong fact: "FORCE is set", not "this role cannot remove the policy".
- **Recommendation:** Treat `OwnedByRole` as a finding regardless of FORCE, or require tenant tables to be owned by a separate NOLOGIN role and assert the app role has no DDL. Add a conformance subtest that attempts `DISABLE ROW LEVEL SECURITY` as the app role and fails if it succeeds.
- **Breaking:** No — stricter verdict; deployments where `AppRole` owns tables must change ownership.
- **Effort:** S

#### SEC-02 — The runtime role has broader registry authority than the API needs, and DSNs are plaintext/mutable
- **Severity:** MAJOR
- **Evidence:** `internal/migrate/migrate.go:277-292` grants `SELECT, INSERT, UPDATE` on both `tenancy.pools` and `tenancy.tenants` to `AppRole`. `db/migrations/00001_registry.sql:76` stores `metadata_dsn text NOT NULL` in plaintext; `tenants.pool_id` and `pools.metadata_dsn` have no immutability trigger (only `security_mode` does, lines 100-119). `internal/scope/scope.go:148-156` uses the same `AppRole` for data-plane `SET LOCAL ROLE` (`internal/pg/scoped.go:180-190`).
- **Why it matters:** If the registry schema is reachable with the same role/credential as a tenant pool (same database, or the same role can connect to both), SQL injection in a tenant query can read every pool's database password, repoint a tenant to another pool, or redirect a pool's DSN. Even without co-location, granting `UPDATE` on the entire registry is broader than the module's own API: `Control` only updates `status` and has no pool-update method.
- **Recommendation:** Use a separate control-plane credential/role and give the data-plane role no registry access. At minimum use column-level grants (`UPDATE (status)` on tenants; no `UPDATE` on pools), add triggers protecting `pool_id` and `metadata_dsn`, and consider encrypting stored DSNs or sourcing them from OpenBao. Document the assumed topology.
- **Breaking:** Yes — grants/roles/configuration change. The severity depends on the answer to Q2.
- **Effort:** M

#### SEC-03 — OpenBao accepts plain HTTP and URL userinfo, so bearer tokens and Basic credentials can travel in cleartext or be logged
- **Severity:** MAJOR
- **Evidence:** `credentials/openbao/openbao.go:294-303` accepts any absolute `http` or `https` URL and never rejects `parsed.User`, query, or fragment. `openbao.go:329` stores `parsed.String()` in `base`; `openbao.go:216-218` and `:844-846` render `Address`/`base`; the invalid-URL error at `:296` echoes `Address`. `net/http` converts URL userinfo into a Basic `Authorization` header, and the vault token is sent as `X-Vault-Token` at `:718`.
- **Why it matters:** `http://` sends both the Basic password and the vault token in cleartext. A URL such as `https://user:password@openbao...` is accepted and will be printed by a startup config log or an error, leaking the Basic credential even over TLS. The vault token can mint database credentials and revoke leases for every pool.
- **Recommendation:** Reject `parsed.User != nil`, query and fragment. Require HTTPS, with an explicit `AllowInsecureHTTP` option only for loopback/dev if needed. Redact userinfo in every error and rendering. Add tests for `http`, userinfo, and a malformed URL containing a secret.
- **Breaking:** Yes — stricter configuration validation; pre-1.0.
- **Effort:** S

#### SEC-04 — The OpenBao HTTP client follows redirects with `X-Vault-Token`
- **Severity:** MINOR
- **Evidence:** `credentials/openbao/openbao.go:319-322` creates a default `http.Client` with no `CheckRedirect`; `openbao.go:714-723` sets `X-Vault-Token` and calls `client.Do`. A local two-server test confirmed the second server receives the token on a 307 redirect; Go strips `Authorization`/`Cookie` cross-host but not custom headers.
- **Why it matters:** A 3xx from the configured endpoint — leader redirect, compromised ingress, or an HTTPS-to-HTTP downgrade — sends the vault token to the redirect target. The token can mint credentials for every pool.
- **Recommendation:** Set `CheckRedirect` to reject cross-host and non-HTTPS redirects (or `http.ErrUseLastResponse`), and apply the same policy when a caller supplies `Config.HTTPClient` (wrap or validate it). Add a test.
- **Breaking:** No.
- **Effort:** S

#### SEC-05 — `Config.String` can leak a custom `Credentials` implementation through `%+v`
- **Severity:** MINOR

- **Effort:** S

#### SEC-06 — RLS is presented as stronger than it is; it is not an SQL-injection containment boundary
- **Severity:** MINOR
- **Evidence:** `internal/pg/scoped.go:42-46` and `tenancy.go:24-25` say a caller cannot forget the predicate "because a caller never sets it". - **Why it matters:** RLS protects against forgotten predicates and application bugs. The docs read as if it also contains SQL injection, which is false, and an adopter may rely on it for the wrong threat.
- **Recommendation:** State the limit explicitly in `SECURITY.md`, `CHARTER.md` and `Scoped.Tx`: RLS is a backstop behind application scoping, not an SQLi containment mechanism. Require the app role to be a non-owner with no DDL, and consider a tenant-context mechanism that caller SQL cannot reset.

#### SEC-07 — A canceled request can leave an issued credential unreleased
- **Severity:** MINOR

#### SEC-09 — Redaction does not cover value copies or YAML/XML; secrets are never zeroized
- **Severity:** MINOR
- **Evidence:** `credentials/openbao/openbao.go:844-866` implements `String`/`Format`/`MarshalJSON`/`LogValue` only on `*Credentials`. ### DOM — Tenancy domain correctness

**Score: 3/5.** The core RLS, reference counting and retirement mechanisms are well designed and tested. The defects below are in the edges: status freshness, what enforcement actually checks, shutdown, and input bounds.

#### DOM-01 — A warm positive cache serves suspended or deleting tenants until TTL
- **Severity:** MAJOR
- **Evidence:** `internal/pool/resolver.go:322-325` returns a cached positive entry without re-reading status; `resolver.go:344` caches the tenant row. The docs at `resolver.go:147-153` say "suspension, which is never cached at all"; `tenancytest/suite.go:456-478` only suspends before the first resolution, so it never exercises a warm entry. `internal/registry/registry.go:298-302` repeats the "never cached" claim.

- **Breaking:** No — behavior tightens; cache lifetime shortens.
- **Effort:** M

#### DOM-02 — RLS coverage and enforcement can report fail-closed without a policy that filters
- **Severity:** MAJOR
- **Evidence:** `internal/pg/enforcement.go:226-236` checks only that a policy *named* `tenant_isolation` exists and that `row_security_active(c.oid)` is true; it never inspects `pg_policy.polpermissive`, `polqual`, or `polwithcheck`. `internal/pg/rls.go:280-290` counts *any* policy. `CheckEnforcement(ctx)` with an empty table list yields an empty `Findings()` and `FailClosed() == true` (`enforcement.go:149,158-177`). `internal/pg/rls_integration_test.go:220-260` only tests "no policy"; `tenancytest/suite.go:1166-1195` likewise.
- **Why it matters:** A hand-edited or drifted policy that permits every row (or every write) still satisfies `PolicyPresent` and `row_security_active`, so a startup gate says isolated while tenant A can read/write tenant B's rows. `AssertRLSCoverage` passes when `tenant_isolation` is dropped but the permissive `tenant_access` companion remains, or when a policy exists but RLS is disabled/unFORCEd. An incomplete/empty table list is vacuously "fail-closed".
- **Recommendation:** Read `pg_class.relrowsecurity`, `relforcerowsecurity`, `pg_policy.polpermissive`, and `pg_get_expr(polqual/polwithcheck)`; require the restrictive tenant predicate in both `USING` and `WITH CHECK`; count only the restrictive tenant policy in `AssertRLSCoverage`; reject an empty table list; consider a positive two-tenant probe in `CheckEnforcement`. Add negative fixtures for permissive-only, wrong predicate, RLS disabled, and owner+FORCE.
- **Breaking:** No — behavior becomes stricter; deployment test lists may grow.
- **Effort:** M

#### DOM-03 — Tenant status has no transition rules; `deleting` can be reactivated
- **Severity:** MAJOR
- **Evidence:** `internal/registry/registry.go:291-316` `SetTenantStatus` validates only that the target is one of the three enum values; it never checks the current status or defines allowed transitions. The schema `db/migrations/00001_registry.sql:88` only has a CHECK on the value set. The docs at `internal/domain/tenant.go:47-67` describe `deleting` as "being torn down and its data erased".
- **Why it matters:** `deleting → active` is accepted, potentially after erasure has begun, and `suspended → active` vs `deleting → active` are indistinguishable to the API. There is no optimistic concurrency, so two operators can race status changes with last-write-wins. A lifecycle enum without a state machine is not a lifecycle.
- **Recommendation:** Define and enforce allowed transitions: `active ↔ suspended`, `active/suspended → deleting`, `deleting` terminal (or explicitly allow an audited restore). Enforce in SQL (trigger) as well as Go, add tests for every invalid transition, and consider a version/updated_at precondition for concurrent updates.
- **Breaking:** Yes — callers that currently reactivate deleting tenants will get an error; pre-1.0 acceptable.
- **Effort:** S–M

#### DOM-04 — `Close` can return before a retired pool is closed and its credential released
- **Severity:** MAJOR
- **Evidence:** `internal/pool/resolver.go:708-727` `release` sets `entry.closed = true`, deletes the entry from `retiredPending`, unlocks, then calls `closeInBackground`. `:776-781` closes the pool inside a fire-and-forget goroutine. `:849-895` `Close` collects only `pools.all()` and `retiredPending`, then returns after synchronous closes. - **Recommendation:** Track background closes with a `sync.WaitGroup` or keep entries in a `closing` set until `db.Close` and `Release` complete; wait for them in `Close`. Add a deterministic test that releases the last borrower concurrently with `Close` and asserts the pool is closed and the credential released before `Close` returns.

## Cross-cutting themes

1. **Security claims are checked by presence or name, not by behavior.** `CheckEnforcement` checks a policy named `tenant_isolation` and `row_security_active`; `AssertRLSCoverage` counts any policy; the OpenBao `CheckRole` is a substring check; `EnsureRole` creates a NOLOGIN role but nothing verifies the runtime role's membership. The module is honest in places about these limits, but the public claims run ahead of the checks.

2. **Documentation is richer than the code's guarantees.** "Suspension is never cached", "creates the one policy", "migrated fresh", "both are rolled back", "every rendering Go offers", and "a caller never sets it" are all contradicted by the implementation. The prose is a strength, but it needs the same test discipline as the code.

3. **Duplicate sources of truth recur.** `Config.Credentials` vs `Cache.Credentials`; `Config.Clock` vs `Cache.Clock`; `mise.toml` vs CI pins; README status vs git tags; `AppRole` in `migrate` and `scope`; facade aliases vs internal docs; `api.txt` exports vs actual reachability. Each duplication is a future drift.

4. **The security boundary is type-level on the query path but not on the credential path.** The control-plane/data-plane split is excellent for SQL, but `Scoped.Pool()` and `Credentials.Issue` hand the same object the DSN. A capability model (PoolRef) is the missing half.

5. **The test suite is strong on known regressions and weak on adversarial cases.** TOCTOU, partial borrow, session reset and RLS vacuity are covered well. There is no fuzzing, no permissive-only/wrong-predicate RLS fixture, no warm-cache suspension test, no empty-table enforcement test, and no transport/redirect test for OpenBao.

6. **Operational maturity is behind code maturity.** No changelog/release workflow, no metrics, discarded release errors, no rollback/upgrade test, one maintainer, and no vulnerability gate. These are the things an external adopter discovers after the code works.

7. **Historical/internal context leaks into the public docs.** `CHARTER.md`, `CONVENTIONS.md`, comments and the README talk to `cas`, `kgs`, `acre`, `iam`, `audit` and `keyring` as if the reader knows them. For an external adopter this reads as insider documentation and hides the actual threat model.

## Open questions for the maintainer

Each question is answerable on its own; the recommendation is what the review would choose if the maintainer has no stronger constraint.

### Q1 — What threat must RLS actually stop: application bugs only, or SQL injection too?
**Context:** The module calls RLS a fail-closed backstop behind application scoping. `CheckEnforcement` only checks that a policy named `tenant_isolation` exists and that `row_security_active` is true; it does not inspect the predicate. `Scoped.Tx` accepts arbitrary SQL, so injected SQL can reset `app.tenant_id` with `set_config`. An `AppRole` that owns a table can disable RLS unless the role is prevented from DDL.
**Why it blocks:** It decides whether DOM-02/SEC-01/SEC-06 are a documentation tightening (application-bug threat) or a P0 redesign (SQLi containment). It also sets the required owner/DDL privileges for every consumer.
**Options:**
- **A (recommended):** RLS is a backstop against forgotten predicates and application bugs. Document that SQLi/DDL-capable roles defeat it. Still require the correct restrictive predicate, enabled/FORCEd RLS, and warn on owner+FORCE.
- **B:** RLS must contain SQL injection. Require a non-owner, no-DDL app role; protect the tenant GUC from caller SQL; add positive two-tenant probes; likely run queries through a narrower interface.
- **C:** RLS is only a compliance/operator check and the SQL path is fully trusted. Least strict; document the assumption.
**Recommendation:** A now, with B as a funded hardening path if untrusted SQL is ever in scope.

### Q2 — Are the control plane and data plane the same Postgres role/DSN in supported deployments?
**Context:** `Migrate.AppRole` is described as the role the control plane and every resolved pool connect as; the reconciler grants `SELECT/INSERT/UPDATE` on both registry tables; `metadata_dsn` is plaintext; `pool_id`/`metadata_dsn` are mutable. If the registry schema is reachable with the same role as a tenant pool, SQL injection in a tenant query can read all DSNs or repoint tenants.
**Why it blocks:** It determines whether SEC-02 is a P0 topology flaw or a P1 least-privilege cleanup, and whether the module should add column grants/triggers or a separate control-plane role.
**Options:**
- **A (recommended):** Separate control-plane role/DSN with registry grants; the data-plane AppRole gets no registry access.
- **B:** Same role, but separate databases and column-level `UPDATE(status)` grants plus triggers protecting `pool_id`/`metadata_dsn`; document the co-location assumption.
- **C:** Keep the current shared role and document the risk as accepted.
**Recommendation:** A. If A is not possible, B is the minimum.

### Q3 — Should suspension and deletion take effect immediately, or is TTL-bounded status acceptable?
**Context:** A positive cache entry is returned without re-reading status, so a tenant resolved while active can be served for the full TTL after `SetTenantStatus(suspended)` or `(deleting)`. The docs say suspension is never cached; the tests only suspend before the first resolution.
**Why it blocks:** It determines DOM-01's fix and the cache API. Immediate invalidation needs a control→resolver notification; TTL-bounded status is simpler but weakens an operator kill switch.
**Options:**
- **A (recommended):** Invalidate the positive entry from `SetTenantStatus`, or revalidate status on every `Scope` under a short status TTL; add resolve→suspend/delete tests.
- **B:** Keep the positive cache but add a short, separate status TTL; document the maximum delay.
- **C:** Treat TTL-bounded status as intended and correct the docs; not recommended for suspension.
**Recommendation:** A.

### Q4 — Who provisions the runtime `LOGIN` role and its membership in `AppRole`?
**Context:** `Migrate` creates `AppRole` as `NOLOGIN`; the README passes a separate `runtimeDSN` but never explains that it must be a `LOGIN` role with membership/inheritance in `AppRole`, or with the registry grants. A clean deployment cannot connect as the `NOLOGIN` role.
**Why it blocks:** It blocks DX-01/DOC-01 and shapes SEC-02. Automating membership requires the migration credential to manage roles, which is a privilege decision.
**Options:**
- **A (recommended):** Document out-of-band provisioning (create a LOGIN role, `GRANT AppRole TO runtime_role`, connect as it) and add a startup check that `SET ROLE AppRole` succeeds and the registry grants are present.
- **B:** Automate membership in `Migrate` (stronger first-run experience, more privilege for the migration credential).
- **C:** Make `AppRole` itself a `LOGIN` role (simpler, but conflates the grantee and the login identity and weakens separation).
**Recommendation:** A plus a startup check; consider B later as an opt-in.

### Q5 — Is plain HTTP to OpenBao ever a supported configuration?
**Context:** `Open` accepts `http` and `https`, URL userinfo, query and fragment. The token is sent in `X-Vault-Token`; userinfo becomes Basic auth. Config logging/error paths can print the address.
**Why it blocks:** It determines SEC-03's validation strictness and whether existing dev setups break.
**Options:**
- **A (recommended):** HTTPS-only, with an explicit loopback/dev exception; reject userinfo/query/fragment and redact the address.
- **B:** Allow HTTP only behind an explicit `AllowInsecureHTTP` flag with loud documentation.
- **C:** Keep the current behavior and document the risk.
**Recommendation:** A.

### Q6 — Should `Scoped.Pool()` return the full pool row, or a `PoolRef` without the DSN?
**Context:** `Scoped.Pool()` returns `domain.Pool` including `MetadataDSN`, so any data-plane holder can open an unscoped connection. `Credentials.Issue` and `OpenBao.RoleFor` also receive the full `Pool`.
**Why it blocks:** It determines the ARCH-03 fix and the custom-credentials API. A `PoolRef` is a breaking change but aligns the capability with the data-plane type.
**Options:**
- **A (recommended):** Return a `PoolRef` (ID, name, region, blob config reference, capacity) with no DSN; pass it to `Credentials.Issue`/`RoleFor`; keep the full `Pool` internal.
- **B:** Keep the full `Pool` and document that handlers must not read `MetadataDSN`; weaker.
- **C:** Remove `Pool()` and expose only ID/region accessors; most restrictive, more API churn.
**Recommendation:** A.

### Q7 — Should `testdb` remain in the root module?
**Context:** The root `go.mod` directly requires testcontainers because `testdb` imports it; every consumer resolves the Docker/moby graph. `testdb`'s public API also names internal `domain.DSN`.
**Why it blocks:** It shapes ARCH-02 and MNT-07. A nested module keeps the import path but requires consumers to depend on the nested version; a separate repository is more breaking.
**Options:**
- **A (recommended):** Nested module `testdb/go.mod`, same import path, exported signatures use `tenancy.DSN`.
- **B:** Separate repository/module path; cleanest graph, breaking for importers.
- **C:** Keep it in the root module and document/scan the test graph.
**Recommendation:** A.

### Q8 — What is the 0.x release and compatibility policy?
**Context:** Tags `v0.1.0`–`v0.3.0` exist, HEAD is untagged, the README says "unreleased", and there is no changelog/upgrade guide. The charter treats `api.txt` as a reviewed boundary.
**Why it blocks:** It determines whether the P1 breaking changes can land now, how they are communicated, and what an external adopter may pin.
**Options:**
- **A (recommended):** 0.x policy: minor may break, patch fixes; `CHANGELOG.md` + upgrade notes per release; tag HEAD only after the full gate.
- **B:** Freeze the API and cut 1.0 now; requires completing P0/P1 first.
- **C:** Continue untagged development; external adoption stays blocked.
**Recommendation:** A until P0/P1 are done, then B.

### Q9 — Is `Readiness` in scope for this module?
**Context:** `Readiness` is public, tested only for `Valid`, unused by the registry or migrations, and its doc claims a charter scope the charter does not list.
**Why it blocks:** It decides whether CLN-01 is a deletion, a move to `iam`, or a charter amendment. Keeping dead public surface in a module trying to become adoptable is costly.
**Options:**
- **A (recommended):** Remove it.
- **B:** Move it to `iam` or the consumer that owns the processing pipeline.
- **C:** Keep it and amend `CHARTER.md` with a concrete registry use.
**Recommendation:** A.

### Q10 — Should tenant status be a strict state machine, and is `deleting` terminal?
**Context:** `SetTenantStatus` accepts any of the three states in any direction, including `deleting → active`; there is no optimistic concurrency. `deleting` is documented as data erasure.
**Why it blocks:** It determines DOM-03's behavior and whether an operator can accidentally resurrect a tenant whose data is being erased.
**Options:**
- **A (recommended):** Enforce `active ↔ suspended`, `active/suspended → deleting`, `deleting` terminal; enforce in SQL and Go; add tests.
- **B:** Only forbid leaving `deleting`; allow the rest.
- **C:** Keep arbitrary operator transitions, with audit logging.
**Recommendation:** A.

### Q11 — What should callers do with permanent privilege/schema errors?
**Context:** The module maps insufficient privilege (`42501`), missing tables/columns and failed `SET ROLE` to `ErrUnavailable`, which it defines as retryable. Callers and retry middleware will retry permanent deployment mistakes.
**Why it blocks:** It determines GO-02 and the stability of the exported error taxonomy. Adding a new sentinel is a public API decision.
**Options:**
- **A (recommended):** Map privilege/role/schema-shape failures to `ErrInvalidConfig` or a new `ErrPermission`; keep `ErrUnavailable` for reachability/suspension; add tests.
- **B:** Keep `ErrUnavailable` but document which causes are permanent; provide a `Retryable(err)` helper.
- **C:** Add a new broad `ErrPermanent` and leave the existing sentinels alone.
**Recommendation:** A.

## Assumptions

- "Production grade" here means safe multi-tenant operation by an external adopter, not merely a passing test suite.
- The module is pre-1.0 and backwards compatibility is not a constraint. Breaking recommendations are intentional and marked; downstream `cas`/`kgs`/`acre` wiring can be adapted.
- The maintainer has chosen separate control-plane and data-plane roles/DSNs (Q2). SEC-02 is therefore P0. No existing deployment was inspected; the recommendation assumes new deployments can adopt the split and that existing ones can migrate their grants.
- OpenBao is an optional adapter. SEC-03/SEC-04/SEC-07 matter only to deployments that enable it; the rest of the module still has the RLS and lifecycle findings.
- Consumer tenant tables are assumed to be created by `EnableRLS` and owned by a migration/owner role, not by `AppRole`. The current code does not enforce that assumption (SEC-01).
- The working-tree toolchain edits (`mise.toml`, `go.mod`, CI) are authoritative, as instructed. The review does not treat the uncommitted state as a defect; it does note that tagged commits and the working tree build differently until the edits are committed.
- The `TenantTx` refutation was tested against a live Postgres container on Go 1.27.3; no password leak was found. The new methods are accepted as a stability improvement.

## What could not be verified

- **Deployment topology.** No existing deployment was inspected to confirm whether the registry schema is reachable with the same role/credential as a tenant pool, or whether they are co-located. The maintainer has chosen separate roles/DSNs (Q2), so the review treats the shared case as unsupported; existing deployments still need a migration check.
- **Real OpenBao behavior.** The redirect-header behavior was confirmed with a local `net/http` two-server test, not against a live OpenBao or a real ingress. OpenBao leader redirects, proxy behavior, and TLS configuration were not exercised.
- **Exploitability/CVSS of the four govulncheck findings.** The scan's symbol traces were used as evidence; no exploit was written. The `x/text` path is production; the `x/crypto`/`moby` paths are testcontainers/testdb. The `openbao.Credentials.String -> archive.init` traces are module-initialization, not runtime calls.
- **Race in `Close`.** DOM-04 is reasoned from the code and the goroutine ordering; it was not reproduced deterministically. The existing race suite passes, but it does not cover the release-vs-Close window.
- **WorkerCapacity overflow and mixed-case role behavior end to end.** Both follow directly from the `int32` cast and PostgreSQL identifier folding; neither was exercised through the public API against a live database.
- **Memory disclosure/zeroization.** No core-dump or memory-inspection test was run. The finding is a defense-in-depth limitation, not a demonstrated exploit.
- **Fuzzing, benchmarks, load behavior, 32-bit builds, non-Linux platforms.** None were run.
- **Remote repository state.** The user stated `main` is the only remote branch and there are no open PRs; the review verified local tags and HEAD but did not query GitHub branch protection, CODEOWNERS, or remote PR state.
- **External adoption.** No external consumer was run against the suite. The charter's `cas` swap is still pending, so the claim that the suite works against a consumer's own wiring is not independently demonstrated here.
